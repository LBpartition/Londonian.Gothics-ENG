 0. GROUND RULES
--------------------------------------------------------------------------------
 - Nothing from the previous failed attempts is treated as fact. Every offset,
   format, control code and limit is re-derived from the clean ROM and backed
   by evidence (hash, hex dump, disassembly excerpt, render, or screenshot).
 - The clean Japanese ROM is never modified. Its SHA-256 is recorded and
   re-checked before every build.
 - Translation text comes ONLY from ShadowRisae's GameFAQs script (FAQ 75947).
   No machine translation, no invented paraphrasing. Where the script has no
   matching line, the entry is flagged for a human decision.
 - Every tool must round-trip: unpack -> repack with no edits must reproduce
   the original bytes exactly. No tool is trusted until it does.
 - No text is ever silently truncated or skipped. Anything that cannot be made
   to fit automatically is flagged for review.
 - Runtime testing: I may install and use a DS emulator myself, but only via
   SCRIPTED interfaces (e.g. BizHawk/DeSmuME Lua: load ROM, feed inputs,
   take screenshots, read RAM) - never blind GUI clicking. Static analysis of
   the binaries remains the primary method; you do final playtesting.
   Screenshot rules: captured from the emulator framebuffer via script (NOT
   desktop/window capture), at native 256x384 (both screens, top over
   bottom, upright), on an exact frame reached by script-controlled frame
   stepping, with the frame number in the filename. Preferred emulator:
   BizHawk (melonDS core) - Lua: joypad.set, emu.frameadvance,
   client.screenshot, memory reads. Fallback: DeSmuME Lua.
 - Each phase ends with a short report + evidence and a gate (pass/fail) before
   the next phase depends on it.

 Known (user-observed, to be confirmed in code):
 - Dialogue and descriptions are limited to 2 lines per box at the current
   glyph size/spacing.
 - The font may already contain English glyphs.

================================================================================
 PHASE 1 - ROM BASELINE & FILESYSTEM                        ETA: 1-2 hours
================================================================================
 Goal: a verified, reproducible unpack/repack of the ROM.

 Steps
 1.1 Copy the supplied ROM into .REFS (read-only) and .WORK.
 1.2 Record SHA-256/CRC32, header fields (title, game code, ARM9/ARM7 offsets
     and sizes, FNT/FAT, overlays, banner, ROM size field).
 1.3 Extract everything with ndstool (or an equivalent, scriptable tool):
     arm9.bin, arm7.bin, overlays, y9/y7 tables, banner, header, data/ tree.
 1.4 Generate a manifest (CSV/JSON): file ID, path, ROM start/end, size,
     alignment gap to next file, magic bytes, SHA-256.
 1.5 Round-trip test: rebuild the ROM from the extracted files with no edits.

 Deliverables: manifest.csv, header report, extraction scripts.
 Gate: Rebuilt ROM is byte-identical OR differences are fully explained
       (e.g. padding only) and the rebuilt ROM boots identically in melonDS.
 Your part: boot the round-trip ROM once (~5 min).

================================================================================
 PHASE 2 - FONT / GLYPH DISCOVERY                           ETA: 3-8 hours
================================================================================
 Goal: a complete, verified glyph table (glyph ID -> character, width).

 Steps
 2.1 Locate the font data (search data/ files and ARM9 for graphics that look
     like tiled 1bpp/2bpp/4bpp glyph sheets; confirm via the code that loads it).
 2.2 Determine the format: glyph cell size, bit depth, any per-glyph width
     table, ordering.
 2.3 Dump every glyph to a labelled PNG contact sheet (glyph ID under each).
 2.4 Build the character table:
       - Auto-label kana/kanji where possible by matching known strings.
       - Identify existing English/Latin glyphs (upper/lower case, digits,
         punctuation) and their pixel widths.
       - You spot-check the sheet; ambiguous glyphs listed for review.
 2.5 Font changes are decided by testing, not assumed. If the existing
     English glyphs are sufficient, the font is left untouched.
     Only if extra glyphs are needed (e.g. digraphs, missing punctuation):
     run small tests to determine whether appending new glyphs or reusing
     unused slots is safer, then choose. ROM may be expanded to 128 MB if
     extra space is ever required.

 Deliverables: font_sheet.png, glyph_table.tsv (id, char, width, notes).
 Gate: Decoding a sample of known on-screen text with the table reproduces
       exactly what is shown in-game (compared against your screenshots).
 Your part: 2-4 screenshots of specific screens; review the sheet (~30 min).

================================================================================
 PHASE 3 - TEXT RENDERER & LAYOUT ANALYSIS                  ETA: 4-10 hours
================================================================================
 Goal: know exactly how text is drawn, so fitting decisions are based on code,
 not guesses.

 Steps
 3.1 Find the routine(s) that read text and draw glyphs (static disassembly of
     arm9.bin/overlays; Ghidra or equivalent).
 3.2 Document every control code: line break, new box / wait-for-button,
     end of string, speaker names, colours, pauses, variables, etc.
 3.3 Measure the layout: glyph advance (pixels), line height, box width,
     max lines per box (confirm the 2-line limit), any per-box character
     buffer limits.
 3.4 Determine whether glyph advance is fixed or per-glyph, and where that
     value lives. Assess options:
       a) Reduce fixed advance for narrow Latin glyphs (small code patch).
       b) Variable-width font (VWF) - per-glyph widths (larger code patch).
       c) Digraph glyphs - two letters drawn in one glyph slot (no code patch,
          needs extra glyphs; method decided by testing per 2.5).
     Recommend one, with risk assessment.
 3.5 Check buffer sizes so longer strings cannot overflow RAM.

 Deliverables: renderer_notes.txt (addresses + disassembly excerpts),
               control_codes.tsv, layout_limits.txt, fit-option recommendation.
 Gate: A tiny hand-made test (e.g. one line edited to "ABC abc" plus a forced
       new box) displays exactly as predicted in melonDS.
 Your part: run 1-2 test ROMs, send screenshots (~15 min each).

================================================================================
 PHASE 4 - FONT / SPACING IMPROVEMENT (decision from 3.4)   ETA: 2-10 hours
================================================================================ 
 Goal: fit as much English per line as safely possible.

 - Option a (narrower advance): ~2-4 h.
 - Option c (digraphs): ~3-6 h (generate glyph art from a pixel font,
   build digraph pairing table from the English script's letter frequencies).
 - Option b (VWF): ~6-10 h (ASM hook, needs most testing).
 If the existing English glyphs are already narrow/variable width, this phase
 may shrink to under an hour.

 Deliverables: font patch, updated glyph_table.tsv, sample renders.
 Gate: Test screen in melonDS matches the preview renderer pixel-for-pixel.
 Your part: visual approval of the look (~15 min).

================================================================================
 PHASE 5 - SCRIPT FORMAT (.sp etc.) PARSER / REBUILDER      ETA: 4-12 hours
================================================================================
 Goal: fully understand every text-bearing file format, not just find strings.

 Steps
 5.1 Identify every file type that contains text (dialogue scripts, menus,
     item/dress descriptions, ARM9 embedded strings, graphics with baked-in
     text such as title/menu images).
 5.2 For each format, reverse the structure: header, record table, pointers/
     offsets, opcodes (script commands vs. text), terminators.
 5.3 Write parser -> structured JSON, and rebuilder JSON -> binary, which
     recomputes all pointers/lengths so records can grow or shrink freely.
 5.4 Confirm how to insert an extra box (button wait) mid-dialogue.
 5.5 Round-trip EVERY file of each format.

 Deliverables: format specs, parse/rebuild tools, round-trip report.
 Gate: 100% of files rebuild byte-identical from their parsed form.
       A test where one record is made 3x longer still runs correctly in-game.
 Your part: run the growth test ROM (~10 min).

================================================================================
 PHASE 6 - MASTER TEXT DUMP                                 ETA: 2-4 hours
================================================================================
 Goal: one human-readable, traceable dump of all Japanese text.

 Format (one entry per line block / spreadsheet row):
   ID | file | record/offset | context (speaker, scene) | Japanese text
      | control codes shown as tags e.g. {BOX} {NL} {NAME}
 Outputs:
   japanese_master.tsv  (machine source of truth)
   japanese_master.txt  (easy reading)
 This file is also the base for future translations into other languages.

 Gate: Re-encoding the dump without changes reproduces the original files.
 Your part: skim for obvious garbage (~20 min).

================================================================================
 PHASE 7 - GAMEFAQS SCRIPT ALIGNMENT                        ETA: 4-10 hours
================================================================================
 Goal: an English file with the same IDs/format as the Japanese master.

 Steps
 7.1 Fetch and save the GameFAQs script into .REFS (local copy for reference).
 7.2 Parse it into ordered blocks (scene, speaker, line).
 7.3 Align to the Japanese master by scene order, speaker, and length cues;
     produce suggestions with a status: exact / probable / unmatched.
 7.4 Review pass: you (and I) confirm probable/unmatched entries.
 7.5 Menus/UI/items not in the guide are listed separately for your decision.

 Deliverables: english_master.tsv (same IDs), alignment_report.txt.
 Gate: Every in-scope entry is either matched or explicitly flagged.
 Your part: the biggest human task - reviewing flagged matches
            (estimate 2-6 h depending on script coverage).

================================================================================
 PHASE 8 - AUTO-FIT ENCODER & PREVIEW RENDERER              ETA: 3-6 hours
================================================================================
 Goal: turn english_master.tsv into game-ready records that always fit.

 Fitting order (reject is the LAST resort, never truncation):
   1. Word wrap by real pixel width (using the glyph table).
   2. Split into extra boxes when more than 2 lines (box breaks placed at
      sentence/clause boundaries where possible).
   3. Use the spacing/font improvement from Phase 4.
   4. Records grow freely thanks to the Phase 5 rebuilder.
   5. Fixed-size UI fields that still don't fit -> flagged with suggested
      abbreviation for your approval.
 Also checks: unmapped characters, illegal control codes, buffer limits.

 Preview renderer: draws every box as a PNG using the real font, so the whole
 game's text can be reviewed without playing.

 Deliverables: encoder, preview PNGs, fit_report.txt (flags only).

 RISKS & MITIGATIONS

 - Unknown/compressed formats        -> identify compression early (Phase 1
                                        manifest magic bytes); write codecs
                                        with round-trip tests.

                                        pattern-guessing strings.
 - 2-line boxes too small            -> extra boxes + Phase 4 font work.
 - Fixed-size UI fields              -> abbreviations approved by you, or
                                        code patch if a field is critical.
 - GameFAQs script gaps/ordering     -> explicit unmatched flags; you decide.
 - Emulator vs hardware differences  -> test on melonDS; optional flashcart
                                        test before release.
 - Hardcoded text in ARM9/overlays   -> handled as a separate format in Phase 5
                                        with pointer tracing.
